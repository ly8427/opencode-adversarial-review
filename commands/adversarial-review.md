你的任务是执行一次对抗性审阅流程。根据参数（$ARGUMENTS）分派：

- 参数为空，或以 `focus` 开头 → 执行下面的 **审阅流程**
- `status` → 运行 `node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" status` 并把输出整理给用户
- `history` → 运行 `node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" history --limit 20` 并把输出整理给用户
- `config` → 运行 `node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" config-check` 并把输出整理给用户

（若 `${CLAUDE_PLUGIN_ROOT}` 未被展开，用本插件的实际安装路径替换它。）

## 审阅流程

1. **确定被审对象**：默认是本回合你给出的最终回答。如果用户在参数里点名了更早的结论或方案，以用户点名的为准。
2. **写出被审文本**：用 Write 工具把被审回答的**全文**写入系统临时目录下的文件（不要写在项目目录里，例如 `%TEMP%/adv-review-input.md` 或 `/tmp/adv-review-input.md`），审阅结束后删除该文件。
3. **运行冷审阅**（审阅者是一个无对话历史、无工具的独立 `claude --bare` 进程，由 CLI 派生）：

   ```
   node "${CLAUDE_PLUGIN_ROOT}/src/cli.mjs" review --file <被审文本路径> [--focus "<用户指定的攻击方向>"]
   ```

   如果用户在本轮对话中明确提出过要求或约束（即"本轮用户的问题"），把它作为 `--context "<原文>"` 一并传入——审阅者看不到我们的对话，缺了它会把"缺上下文"误判为"结论错误"。

4. **逐条回应审阅发现**（这是流程的核心，不可跳过）：
   - 对每一条发现，明确标注三者之一：**接受**（说明你要怎么改，然后真的去做）、**反驳**（给出具体依据，如代码位置、测试结果、文档出处）、**待验证**（说明缺什么证据、打算怎么补）。
   - 禁止为了省事整体接受或整体驳回；禁止无视发现直接结束回合。
   - 审阅者的发现只是"有依据的异议"，不是最终裁决——反驳是正当且被鼓励的，但必须给依据。
5. **无发现时**：如实告知"对抗性审阅完成：无实质问题"，不要为了显得有价值而硬凑问题。审阅输出 `verdict=no_material_findings` 是正常且常见的结果。
6. **清理**：删除第 2 步的临时文件。

## 边界

- 审阅者**没有工具、没有对话历史**：它只看传给它的材料。发现里说"材料里没有提到 X"不等于"你没做 X"——回应时先核对事实。
- 审阅结果与被审文本的版本哈希绑定（输出里带"审阅对象版本"）。回答内容修改后重新审阅才是对新版本的意见，旧结果不自动适用于新版本。
- 审阅失败（命令报错/超时）时如实告知用户，不要假装审阅通过。
